## 1. 实验概览与统一度量口径

- **评测对象**：P5 负责的 9 个完整实验配方（`05, 10, 15, 20, 25, 30, 35, 40, 45`）× [tasks_8.json](../../data/tasks_8.json) 中冻结的 8 个 SusVibes 仓库任务 = **72 个独立评测组合**。
- **生成配置**：与 P1 / P2 / P3 / P4 主实验保持一致口径——模型 `deepseek-chat`，单次种子运行，`max_steps=60`，未启用 `rescue` 二次评测（`--no-rescue`）。
- **代码冻结**：实验全程未修改 `harness_sec/`、`configs/`、`data/tasks_8.json` 或上游 `susvibes`（固定于提交 `5d957e6f1850595623d551d089193532e6fa60ce`）。
- **覆盖率与状态**：全部 **72/72** 个预测补丁均成功完成生成与官方 SusVibes 容器评测，所有 72 份报告均为 `eval_status="tested"`、`error=null`，空补丁数为 `0`（补丁大小范围 `638`–`5541` 字符），无容器挂起或任务缺失（对比 P4 在 Windows 宿主机原生生成时受 `mode` 变更与 `ceph` 符号链接删除伪影影响，后经清洗伪影并重评 `wagtail_5c7a` 与 `ceph` 补齐 8 任务口径）。

### 运行环境隔离说明

为避免 Windows 宿主机下的 POSIX 接口缺失（如 `os.sysconf`、`os.uname`）及 `ceph` 等仓库在 NTFS 下检出 1100+ 符号链接触发 `MAX_PATH` / 权限异常，本次主实验在隔离 Linux 容器（Python 3.12 + Docker socket + Linux ext4 卷）中按原样运行 `harness_sec.run_recipe` 与 `harness_sec.evaluate --local-images --no-rescue`，完整使用官方 8 份本地评测镜像 `songwen6968/susvibes.x86_64.eval_*`。

## 4. 关键机制发现与跨组对比

1. **`k2`（任务安全卡）成为 P1 / P2 / P3 / P4 / P5 全组共识优胜前置条件，其中 P5 的 `25 (k2+p+F)` 创下全部 48 组最高 Joint 4/8**：
   - 在 [all_results.csv](../all_results.csv) 全部已归档 48 组配方中，P1 最高 `Joint` 为 `2/8`（`21: k2+l2+F`、`26: k2+p+C`、`31: k2+e+A`），P2 最高为 `2/8`（`22: k2+l2+C`、`27: k2+p+A`、`32: k2+e+S`、`17: k2+l1+F`），P3 最高为 `2/8`（`28: k2+p+S`），P4（清洗后 8 任务口径）最高为 `2/8`（`19: k2+l1+A`、`29: k2+e+F`）——全部五个实验组最高联合通过率均出自 `k2` 配方。
   - P5 的 `k2` 组（`20, 25, 30`）联合通过率分别达到 `1/8`、`4/8`、`2/8`（组均 `2.33/8` = `29.2%`），明显领先于同批次 `k1` 组（`05, 10, 15`，组均 `0.33/8` = `4.2%`）与 `k3` 组（`35, 40, 45`，组均 `0.33/8` = `4.2%`）。
   - 最优配方 `25`（`T-P-F`：`k2+p+F`）在 `markdown-it-py`、`wagtail_5c7a609`、`wagtail_bc96aed` 与 `plone` 四个任务上均同时通过功能与安全验证（`SecPass|FuncPass = 0.800`），且仅耗费 `1.38` 次平均尝试、`0` 次拦截与 `¥0.595`（9 个配方中成本最低）。
2. **高功能通过率不自动带来高安全通过率**：
   - `10`（`k1+p+C`）与 `15`（`k1+e+A`）拿下 P5 最高的 `FuncPass = 6/8 (0.750)`（包括全组唯一在 `aiohttp-session` 上通过功能测试的 `10`），但两者 `SecPass` 与 `Joint` 均为 `0/8`，原因在于 `k1` 仅给出通用安全原则而缺乏针对任务威胁面的具体约束（如 `wagtail_bc96aed` 仅在 `25` 中被修复）。
3. **重度上下文/审查循环的代价与过度拦截**：
   - `40`（`k3+l2+S`）平均发现 `4.12` 个问题，触发 `6/8` 次 `blocked` 拦截（最终 `Joint = 1/8`）。
   - `30`（`k2+e+C`）触发高频多轮修复（总计 `40` 次尝试、平均 `5.00` 次、`408` 次 LLM 调用、花费 `¥3.509`），最终取得次高 `Joint = 2/8`，但性价比显著低于 `25`（`¥0.595` 换取 `4/8`）。
