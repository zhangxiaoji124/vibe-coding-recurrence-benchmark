# 48 组配方实验设计（你们的分工版本）

> 结论：**48 组可以跑，代码已经支持**（`harness_sec/configs/recipes/01–48.yaml`）。
> 但要把三件事定死，否则 48 组跑完会变成"48 个互不可比的数"：① M3 四个水平的定义；② 每组跑多少个任务；③ 和谁比基线。

## 1. 48 = 3 × 4 × 4

| 机制 | 水平 | 说明 |
|---|---|---|
| **M1 知识** | `k1` 通用规则 / `k2` 任务感知威胁卡 / `k3` 仓库感知 | 三选一 |
| **M2 检测** | `l1` agent 自审 / `l2` 独立审查 / `p` Bandit+Semgrep / `e` 自生成探针 | 四选一 |
| **M3 控制** | `F` 反馈表示 / `C` 修复循环 / `A` 安全验收 / `S` 状态保持 | 四选一（见 §2） |

## 2. M3 的四个水平必须"可解释"（关键修正）

原始想法是"M3 四选一 = 只装一块"。但反馈、循环、验收、契约是**同一个控制回路的四层**，只装一块会结构性空转（比如只装 `a` 门禁、没有循环，检测到也没法重做）。所以本仓库把四个水平定义成"**基线循环 + 这一层**"：

| 水平 | 配置 | 含义 |
|---|---|---|
| **F** 反馈表示 | `m3: [f, c]`，2 轮 | 结构化反例 + 重做 2 轮（对照：自然语言反馈） |
| **C** 修复循环 | `m3: [c]`，4 轮 | 只加轮数（自然语言反馈），看"多试几次"值不值 |
| **A** 安全验收 | `m3: [f, c, a]`，2 轮 | 在 F 之上加硬门禁（不过不交付） |
| **S** 状态保持 | `m3: [f, c, a, s]`，2 轮 | 在 A 之上加契约持久化 + 每轮重注入 |

这样 48 组两两之间的差异才是"某一层的有无"，而不是"少写了几行代码"。

## 3. 与"8 臂"的关系（两套设计回答两个问题）

| 设计 | 规模 | 回答 | 用途 |
|---|---|---|---|
| **48 配方** | 48 组 × 8–12 任务 | 哪种**配方**看起来最好？各机制水平的**边际效应**多大？ | 初筛 / 找方向（你们的分工版本） |
| **8 臂** | 2×2×2 × 40 任务 | 机制**开关**有没有用？**交互项**多大？ | 确认 / 归因（论文主结论） |

> 48 组是"地形图"，8 臂是"地质钻探"。**如果时间只够一个：先做 48 组初筛，再用 top-12 做确认**（见 §7）；8 臂可以砍掉或缩成 top 配方确认。

## 4. 和谁比基线（主对照 = 官方可部署增强策略 self-selection）

- ❌ 不能直接比 SusVibes 论文的 11.8%：那是 Claude 4 Sonnet + SWE-agent；
- ❌ 也不该只比"无机制"：那是地板，只能证明"机制有用"；
- ✅ **主对照 = SusVibes 官方唯一可部署的增强策略 `self-selection`**（论文 Table 5：比 generic 安全 +2.7pp，但功能 −7pp；见 `docs/BASELINES.md`）；
- ✅ 次对照 = `generic`（**官方 harness 默认、也是论文的对照基线**）/ 无机制（地板）；
- ✅ 上界参考 = `oracle`（不可部署）。

报告三列：`Δ vs none`（机制有效性）、`Δ vs generic`（超过工程默认）、`Δ vs self-selection`（**超过现有最佳可部署策略**）。

准备官方增强数据集：

```bash
python3 scripts/prepare_official_strategies.py --susvibes-dir ../susvibes \
  --strategies generic self-selection oracle --out-dir data/official
```

跑对照臂时用同一个任务、同一个 agent、同一个评测器，**只换 `--dataset`**。

## 6. 执行（每人只跑自己的组）

```bash
# 先小跑 2 个任务验证通路
python3 -m harness_sec.run_recipe --config harness_sec/configs/recipes/01.yaml \
  --susvibes-dir ../susvibes --limit 2 --out runs/R48/01

# 确认没问题后放量到 8 个任务（同一批任务，所有人一致！）
python3 -m harness_sec.run_recipe --config harness_sec/configs/recipes/01.yaml \
  --susvibes-dir ../susvibes --tasks-file data/tasks_8.json --out runs/R48/01
```

- **所有人必须用同一批任务**（`data/tasks_8.json` 冻结后不许换）；
- 跑批期间冻结代码；
- 回传：`predictions.jsonl`、`predictions_first.jsonl`、`*/episode.json`；
- 官方评测由 P5 统一跑（避免环境差异）。

## 7. 分析（`harness_sec.analyze_recipes`）

```bash
python3 -m harness_sec.analyze_recipes --eval-root ../susvibes/logs/eval --out results/R48
```

输出两张表：
1. **配方排名**：每组 n、FuncPass、SecPass + Wilson 95%、Joint、ΔSec/ΔFunc vs 基线；
2. **机制边际效应**：把 48 组按 M1/M2/M3 水平做平均 → 回答"知识用哪种、检测用哪种、控制用哪种"。

预期能回答你们的问题：
- **harness 应如何提供安全知识** → M1 三个水平的边际 SecPass 差；
- **如何获取安全证据** → M2 四个水平的边际差（尤其 P/E 与 L1/L2 的差）；
- **如何控制开发过程** → M3 四个水平的边际差（F/C/A/S 的增量）。

## 8. 确认阶段（top-12）

初筛后挑 **SecPass 最高 + 成本可接受**的 12 组，在 24–40 个任务上重跑（每组 1 次即可）：

- 目的：把"初筛的方向"变成"有区间的结论"；
- 判据：top 配方 vs 基线的 **ΔSecPass 的 95% 区间下界 > 0**，且 FuncPass 下降 ≤5pp；
- 可选：对 top-3 配方再跑 8 臂拆解（哪个机制贡献最大）。

## 9. 局限（必须写进论文）

1. 每组 n=8–12，SecPass 的 95% 区间约 ±25–35pp → **只能看方向，不能宣称"第 N 组最好"**；
2. 单种子、单模型（Flash）→ 不能外推到其他模型；
3. 48 组的 M3 是"层"不是"纯单块"→ 与文献里的"单策略"不可直接对齐；
4. 基线对比只在本 harness/本 agent 内有效；
5. 任务子集（8–12 个）是 SusVibes 的一个可跑子集，不是全体。
